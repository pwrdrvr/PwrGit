1 The half a first run is still missing, and the four steps that close it

PR #248 fixed where a new user lands: a window with no remembered lens opens in All, and a lens that cannot be filled yet is dimmed and inert rather than spending a click to say nothing. What it could not fix is that the sentence waiting there is the only instruction PwrGit ever gives. “add a folder above” is correct and is not enough — it does not say which folder, how far down PwrGit will look, or that pointing the app at a home directory will not open .ssh. This turn sets the step model; turns 2–5 draw the steps; turn 6 walks the whole thing live.

2 Welcome, and Step 1 — Identity

Welcome states the deal and gets out of the way. Step 1 is the shortest step and the only one that can be wrong silently: PwrGit already seeds a commit e-mail out of ~/.gitconfig at ensureSeed time and has never shown it to anyone. Card 2d is the finding that shaped the rest of this step — the seed reader is not section-aware and does not follow include, so the value it shows can be a forge handle, a stale default, or nothing at all while git config user.name answers fine.

2dFinding — what the current seed reader actually reads
A · identity lives in an included file
[include] path = ~/.gitconfig.d/identity [core] editor = nvim
seeds {} — while git config --get user.name answers Dana Whitfield.
B · a section before [user] carries a name key
[github] name = dwhitfield [user] name = Dana Whitfield email = dana@example.com
seeds the forge handle as the author name, and the e-mail from a different section: dwhitfield <dana@example.com>.
C · conditional include per directory
[user] name = Dana Whitfield email = dana@example.com [includeIf "gitdir:~/work/"] path = ~/.gitconfig-work
seeds the global default, which is right for ~/code and wrong for every repo under ~/work — the second root this same user adds two steps later.
not section-awarereadGitIdentityDefaults takes the first name = and the first email = anywhere in the file, by regex, with no notion of which section they are in. The two can come from different sections.
does not follow includesOne readFileSync of one path. include, includeIf, the system config and any per-repo override are all invisible to it.
remedy · ask gitRead through git config --get user.name. It resolves sections, precedence and includes, and it is the same answer the commit will actually carry. The wizard already shells out to git constantly; this is not a new dependency.
remedy · say where fromA one-line provenance under each field (2b) turns a silent wrong default into a visible one. Where a conditional include exists, name it: that is the notice in 2b.
Verified, not assumed. All three configs above were run through the exact regex in apps/desktop/src/main/profiles/git-identity.ts. A → {}; B → {name:"dwhitfield", email:"dana@example.com"}; C → {name:"Dana Whitfield", email:"dana@example.com"}. The reader is documented as “best-effort… returns empty when unreadable”, which it honours — the gap is that a best-effort value has never had a surface that admits it is one. That is exactly what Step 1 is for.

3 Step 2 — Forges, in the four states they are actually in

This step is a report, not a form. PwrGit reads forges through gh and glab; those CLIs own the credential, so the wizard cannot sign anyone in and must not pretend to. Every sentence below is the one ForgeProductSection.tsx already writes, reused verbatim — a wizard that invents second phrasings is how “Signed out” and “No host is signed in” end up disagreeing on the same screen. The step is skippable in one click: PwrGit is a git client before it is a forge client, and a user with no gh gets a working sidebar anyway.

Two rules this step must not break. A dot is never the only channel — every state that needs attention also says so in a word, because the dot is aria-hidden. And an unprobed product gets neither dot nor word: “we have not looked yet” is honest, and a green dot would be a guess. Both are already load-bearing in the Settings nav, and the wizard is a second consumer of the same read (forge:status), not a second implementation of it.

4 Step 3 — Repo folders. Teach first, then ask.

This is the step the app exists for, and the only one where a user is asked to point software at their disk. “Add a folder” is alarming until you know what the folder is for and what will be opened — so the explanation comes before the picker, not in a tooltip beside it. Every number and every name below is read out of apps/desktop/src/main/git/repo-indexer.ts: MAX_SCAN_DEPTH = 5, the nine-entry SKIP_DIRS set, and the rule that anything starting with . is skipped.

You name folders. PwrGit does the finding.

You will not add repositories one at a time. Point PwrGit at the folder your code already lives in and it walks it, indexing every git checkout it meets — and every worktree each one owns.

1
It looks five levels down. From the folder you add, PwrGit descends up to five levels looking for a .git entry. Once it finds one it stops there — it does not walk around inside your repositories.
2
Hidden folders are never opened. Anything whose name starts with a dot is skipped outright — .ssh, .config, .aws, .gnupg. PwrGit does not look in them, so adding your home folder cannot reach your keys.
3
It reads folder names, not files. The scan lists directory entries and checks for .git. It never opens, reads, copies or sends the contents of anything.
ⓘ
Also skipped, at every level: node_modules, dist, out, build, target, vendor, .cache and macOS Library.

That last paragraph is the wizard paying off #248 directly: the dimmed lenses on the next screen now have a reason the user has already read, instead of four grey chips they have to guess at.

Why the explanation is a step and not a tooltip. The picker asks for filesystem access in the only vocabulary a user has for that request — the one they learned from installers that wanted more than they needed. A tooltip is read after the decision. Putting the three facts on their own screen costs one Continue and buys the difference between “why does it want my home folder” and “oh, it skips dotfiles”. If it must collapse, collapse 3a into 3b as a persistent panel beside the picker — never into a disclosure.

5 Done — show them the thing they just built, without lying about it

A wizard that ends on “Setup complete” has spent the user’s attention and given nothing back. This one ends on their actual sidebar — and the interesting constraint is that the sidebar at that exact moment is not yet the sidebar they will have tomorrow. Per-worktree git state is computed lazily on expand (the premise of #248), and nothing gets pinned by a scan. So 5a draws what is true at Done, 5b draws what it becomes, and the difference between them is the Done screen’s whole job. Every name is contrived fixture data.
