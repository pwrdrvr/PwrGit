Brief, and the six decisions this board needs

The brief (Harold, 2026-11-13). Onboarding is rough for someone who does not know how to get their repositories in. Offer to find them, looking a level or two deep. If they leave the wizard, the empty window should give them buttons that get them going again: add folders, find my repositories, clone from my account. Creating a new repository, on a forge or locally, is not possible in the UI today; that is a separate board and thread, and this one only reserves its place. Everything here was checked against main @ 34068a8f (0.58.0). Names and paths are contrived.

  1. Three levels, not two. Decided 2026-11-13. The search costs nothing measurable at either depth, and two levels misses the ~/github/owner/repo layout the wizard itself calls expected. Evidence in 2a.
  2. Documents, Desktop and Downloads are asked for, not assumed. macOS shows a permission prompt the first time an app opens each one. Recommended: leave them out of the first search and offer them as one button on the results. 2b.
  3. The search is a button, never automatic. Reading the home folder is something the user says yes to. One click, and nothing is added until they confirm the list. 3a.
  4. Closing the wizard still means "do not show this again". That rule was deliberate and stays. The start screen in turn 4 is the safety net, and it holds every door the wizard had. 4a.
  5. The search never looks inside a repository. Added 2026-11-13. Submodules and worktrees checked out inside a repository, such as .claude/worktrees, are not reached, not counted and not proposed. The rule, the edge cases and what it was measured against are in 2e.
  6. Clone, Fork and New repository stop requiring a folder first. Each one can create the folder it lands in. This is also the seam the New repository board plugs into. 5a.

2

Find my repositories: a shallow search that proposes folders

PwrGit's model is folders, not single repositories: you add a folder and it finds what is inside, now and later. So the search does not add repositories. It looks through the home folder, works out which folders hold them, and offers those as a checklist. Nothing is added until the user confirms it.

  • So the headline here is 198 repositories, not 240. The count is repositories after each worktree is folded into its own. It must equal what the sidebar shows once the folders are added.
  • Not stopping would have been wrong and slow. It adds 58 rows that are not the user's repositories, a quarter again on top, and the walk took 1.3 seconds against about 40 milliseconds.
  • The rule to hold with a property test, using the real scan as the oracle: for any generated tree, no proposed folder lies inside a repository, no directory inside a found checkout is ever listed, and the repository count for the checked folders equals what rescanProfile indexes after adding them.

Two limits that exist today and stay. A separate clone kept inside another repository is invisible to the real scan too, since it also stops at .git; here that is 17 clones. And a bare repository with worktrees beside it (proj/.bare, proj/main) is skipped by the scan, which drops a repository whose main entry is bare. That one is read from repo-indexer.ts, not run. The search should show such a folder unchecked and say PwrGit cannot show it yet, rather than promise it.
