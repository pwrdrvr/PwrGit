1 Findings — one chip, four rules it was breaking

PR #211 adds a crosshair locator beside every tag and puts one prominent tag chip on the tagged commit. The locator is the right affordance and the one-chip cap is the right call. The chip it lands you on was the problem: it was drawn as a new thing rather than as the thing it already is — a ref chip, sitting on a line that already has three of them. Every specimen below is reproduced at shipped size from the real CSS, in PwrGit's own font stacks.

1aOne commit's meta line — before, then after
1Before .commit-tag--release
#412 # release‑2026.09.02‑nightly HEAD feat/tag‑locate

Two # tokens in the same mono face, 8px apart, meaning different things — #412 is a pull request, # release‑… is a tag. The tag name is also cut mid‑glyph with no ellipsis, and the chip is the one item on the line that will not give up width.

2After .commit-tag--tag
#412 release‑2026.09.02‑nightly HEAD feat/tag‑locate

Mark plus name, opaque, bordered — the construction .ref-chip beside it already uses. One # left on the line, and it means what it has always meant. The accent moves onto the mark, so the chip still outranks a branch chip without tinting the surface its name has to stay legible against.

--accent-soft is a 12% tint, so a chip painted with it composites over whatever the row is already painting — and this row paints four tints of its own. Light theme therefore failed on a selected row and on a focused‑and‑hovered one, and cleared the floor by less than a rounding error everywhere else. Locating a tag both selects and focuses its row, so the failing states were the ones the feature exists to produce. Dark theme was never at risk; a design that is only checked in dark would have shipped this.

An opaque --bg-panel-elevated takes the row back out of the sum. --text-primary on it is 17.19:1 dark and 17.99:1 light in every state, and --accent on it clears SC 1.4.11's 3:1 for the mark (8.07 / 5.19).

3 What the locator says out loud

Locating is a context change with no focus move, and from the refs browser it also tears down the dialog the reader was standing in. Everything that confirmed it worked was visual.

A

The jump announces

The reveal now speaks through lib/announce.ts: “Tag v2.10.0 located at commit fb92f40, Release milestone commit.” One polite live region, the same one the sidebar reorder uses (SC 4.1.3).

B

A disabled locator says why

title is hover‑only and assistive tech reads the label over it, so “Locate tag source‑tree in lineage” on a permanently dimmed button was a promise the control would not keep. The name now carries the reason: … unavailable, this tag points at a tree, not a commit.

C

No handler, no button

Both surfaces took an optional onLocateTag and rendered a dead, disabled button without it. A control that can never act is worse than no control — its disabled state has no cause the reader can see.

D

Still open: the tags that get no chip at all

readGraphTags keeps one tag per commit and only when it scores above zero, so a commit carrying nightly or build/123 and nothing else draws no chip — the graph reads as if it were untagged — and a commit carrying four release tags shows one with no sign of the others. The branch chips on the same line solve exactly this with a +N pill whose tooltip lists everything. Left for the author: it is a product call about how loud tags should be, not a rule the chip was breaking.
