1Findings: Other worktrees is the one list with no cap, and its top rows are the work that already landed

Branches, tags and remote branches each show a slice of 6 and then a “View all” button. Pull requests split into Local and a collapsed Remote‑only group. Other worktrees is a disclosure that shows every row when you open it (RepoRow.tsx:1045, remaining.map(renderWorktree), with no slice). Its “Recent” order sorts by HEAD’s commit date, so a branch merged twenty minutes ago is the newest thing in the list. Measured on PwrAgnt’s 202 checkouts, 5 October.

1bFour findings
1

No cap, and the order promotes finished work

“Recent” is git log -1 --format=%cI on HEAD (worktree-state.ts:505). Work that merged today was also committed today, so it sorts above every older branch that is still in flight. On PwrAgnt the first five rows are four finished worktrees and one live one.

2

Most of the list is finished

Of 202 checkouts: 145 track a branch that is gone and 35 are detached (28 of them at a commit already in main). 15 track a live branch and 7 were never pushed. 31 of the finished ones still have uncommitted tracked changes, so “finished” cannot simply mean “safe to hide”.

3

gone + open PR is stale PR state. The gone half is right

The real branch behind #803 is deleted on origin (ls-remote finds nothing), and its PR merged at 13:02. gone comes from fetch --prune, which is immediate. The PR chip comes from branch_pr, on a 10‑minute repo TTL. For up to that window the row says both things. Separately, gone and merged together say the same thing twice.

4

Selecting a hidden row opens the disclosure, and saves it open

RepoRow.tsx:373 calls setWorktreesOpen(true) whenever the selection lands in remaining, and that state is saved to localStorage. This is finding 2 of Back Forward Navigation, and its ghost row is the fix. A capped list needs that fix even more, because “open the disclosure” would no longer reveal the row.

2The cap: six in‑flight rows, finished work counted, and View all

The ref sections already answer “how much do I show”: a slice of 6, then a button into the browser. Worktrees get the same answer, with one rule added. Finished worktrees never take a slot. They are counted on a row of their own, and that row is a way into the browser filtered to them, where Prune is one button away. The sort chip and drag order keep working, but only over in‑flight rows. Pinned rows sit above, as now, and are not capped: you pinned them.

4gone and the PR chip: one lifecycle word per row, and gone makes the PR check itself

Finding 3 is a freshness gap between two signals, not a false gone. Close the gap at its source: when a branch’s upstream turns gone while its cached PR is open, refresh that branch’s PR at the user tier right away, instead of waiting for the 10‑minute TTL. Then let the row say one lifecycle thing: a terminal PR state already implies the branch is gone.

4cFollow‑up, separate from the cap: find a PR pushed under another name
?

Ask the forge for the upstream’s name as well

pr-query.ts asks for headRefName = the local branch name only. When branch.<name>.merge or @{push} names a different branch, ask for that name too, and keep the newest. This finds the HEAD:fix/a-v2 case in 1c. Without it, that worktree has no PR, so it can only ever be finished by ancestry, which a squash merge never satisfies.
