0Brief — the Changes rail's folders are not a tree

Operator, 2026-11-13: “If you have foo/ and foo/bar/ and you collapse foo/ it leaves foo/bar/ expanded as a non-child of it. This really should be a tree like VS Code does.” The rail's groupChanges groups each file by its immediate parent only, so foo and foo/bar are two sibling groups. Folding one says nothing about the other, and the folder's Stage/Discard reach only its direct files.

1

Build it ourselves

VS Code's tree lives in its own vs/base/browser/ui/tree (not a published package), and the React tree libraries bring their own row model, focus model and styling. The rail already owns its rows, actions, context menu and selection. A ~100-line path tree plus depth-driven indentation keeps all of that intact.

2

VS Code's rules, decided here

Compact folders (a folder whose only child is a folder shares its row: packages/shared/src). Folders before files, each in Git's byte order. A folder's count, Stage, Discard, Ignore and Copy path cover its whole subtree, still sent as the listed files by name, never the directory. Indent guides always on, at border-subtle.

3

Folding defaults

Folders start open. A folder of only new files past 10 starts folded, which keeps today's untracked-dump protection without folding a root like src/ just because a refactor touched 40 files. Opening a file from elsewhere (⌘K, history) unfolds the folders above it, like VS Code's scm.autoReveal.

?

Open, not in this round

A List/Tree toggle, arrow-key tree navigation (roles tree/treeitem), and Collapse all. The rows are not focusable today, so roving focus is its own change.
