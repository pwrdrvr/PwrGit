The states that decide whether this feature is good
Forking is mostly edge cases. Each of these is a place the dialog either explains itself or wastes a round trip to github.com.
01 — you already have it
Detected before you press anything
huntharo/react Your fork already exists, made 2 years ago. Forking again returns this same repo.
So the button changes rather than lying: Fork & clone becomes Clone your fork, and the upstream option stays on. If it is also already checked out locally, the row carries the existing path and the button becomes Reveal checkout.
02 — forking a fork
Which repo should upstream point at?
You picked gaearon/react, itself a fork. GitHub will put your fork under it, but the branch you actually want to rebase on is almost always the root.
03 — refused before the request
Named, not a raw CLI failure
You own huntharo/dotfiles — GitHub does not fork a repository into the account that already owns it.
Forking is disabled for acme-corp/billing-api by its organization policy.
Forking on gitlab.com needs the GitLab CLI. Clone is available now — how to set it up.
04 — while it runs
Fork is two remote round trips before a byte transfers
Creating huntharo/react on GitHub
Waiting for GitHub to prepare the fork
Receiving objects — 64%
Adding upstream → facebook/react
Adding repository to PwrGit
The clone phases already exist and parse from Git’s stderr. The two GitHub steps and the upstream step are new, and they are the ones with no percentage — so they get a named step, not a stalled bar.
