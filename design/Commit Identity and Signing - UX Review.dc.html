1 Findings — the footer reports an intention, not a resolution

A PwrAgent PR landed with a GitHub noreply author while PwrGit's Personal profile reads a custom email. Both are correct. An agent hit Author identity unknown on a machine with no Git identity at all, and passed a per-command -c user.email=…noreply…. PwrGit had nothing to do with it, and it had no way to tell anyone. The goal of this review: make "Git outside PwrGit has no identity" discoverable, help set it up deliberately, and make PwrGit's own footer tell the truth, then do the same for commit signing. Every probe below was run against isolated HOME / XDG_CONFIG_HOME fixtures with Git 2.56. Identities are contrived.

1bWhat the probes and the code say
1

PwrGit's -c user.email is enforced against some config and not the rest

It beats repo, worktree, includeIf and global user.email. It loses to author.email / committer.email at any scope, and to GIT_AUTHOR_* / GIT_COMMITTER_* / EMAIL in the app's inherited environment. A PwrGit launched from a shell inherits that shell's env.

$ git config author.email bot@ci.example
$ git -c user.email=rowan@vale.example var GIT_AUTHOR_IDENT
Rowan Vale <bot@ci.example>
$ GIT_AUTHOR_EMAIL=env@x.example git -c user.email=… var GIT_AUTHOR_IDENT
Rowan Vale <env@x.example>
2

"Not configured" fails on Linux and silently invents an identity on macOS

On the Ubuntu machine Git refused to commit. On macOS, with nothing configured, git var exits 0 and makes up an email from the login and hostname. A terminal or agent commit goes out as rowan@Rowans-MBP.local. So git var succeeding is not evidence of a configured identity. The configured-only probe is the same call under user.useConfigOnly=true.

$ git var GIT_AUTHOR_IDENT          # nothing configured, macOS
Rowan Vale <rowan@Rowans-MBP.local>
$ git -c user.useConfigOnly=true var GIT_AUTHOR_IDENT
fatal: no email was given and auto-detection is disabled
3

First-run seeding regexes ~/.gitconfig

profiles/git-identity.ts skips includes, includeIf, XDG git/config and sections. The probe resolved ada@work.example.test from an includeIf file and ada@xdg.example.test outside it. A regex sees neither. Replace it with git config --show-origin --show-scope --get-all, run from a neutral directory.

4

The rebase assistant strips signatures

rebase-assistant.ts passes -c commit.gpgSign=false. Someone who signs every commit gets an unsigned branch back from a PwrGit rebase, and nothing says so. On GitHub with vigilant mode, those commits then show "Unverified". Honour the user's setting, and fail the operation readably when the signer is unavailable.

5

%G? misreports SSH signatures

Without gpg.ssh.allowedSignersFile, an SSH-signed commit reports N, the same as unsigned, plus a stderr error. "Is it signed" has to come from the commit object's gpgsig / gpgsig-sha256 header (one cat-file --batch). "Is it verified" can only come from the forge.

✓

GitHub's verdict is already in a payload PwrGit fetches

The Person card's exact-commit proof calls repos/…/commits/{sha}, and that response carries commit.verification (verified, reason). Signing status on GitHub costs no new request. GitLab needs one /commits/:sha/signature call, where a 404 means unsigned. GitCafe's CLI has no exact-commit read, so it stays unknown and silent.

?

Most PwrGit operations need no identity

Fetch, fast-forward pull and bulk sync create no commits. Pull's autostash falls back to git stash <git@stash> even with useConfigOnly. The ones that do pass the profile are commit, amend, annotated tag, the rebase assistant, and operation continue. That list is the scope of 1c.

2 Commit footer and identity details — three questions, one popover

The as … line stays where it is, at the size it is, and becomes a quiet button. A quiet line means "Git will record exactly this". A dot and a short reason mean "something other than your profile decides". A red block replaces the line only when Git cannot resolve a usable identity, the one case Commit is disabled. Clicking opens the details popover. It answers, in order: Who will PwrGit record? What does Git outside PwrGit resolve here? What is already recorded? Sources and file paths sit behind a disclosure at the bottom.

3 The durable notice — “Git outside PwrGit has no identity”

This is the operator's ask: a toast that stays until it is handled, with one button into Settings. It uses the shipped showInfoToast({ sticky, key, layout: "stacked", action }), so no new toast machinery. It is info-toned, not an error: PwrGit's own commits are fine, and the toast says so first. It speaks for the machine, so main raises it in one window only (the update toast's rule), keyed so a second check replaces it rather than stacking.

5 Commit signing — a cheap “did you know”, and a precise “why not verified”

Signing has three separate facts, and each comes from a different source. Configured? One git config --get-regexp, local and instant. Signed? A gpgsig header on the pushed commits, one cat-file --batch. Verified? Only the forge knows, because it depends on the key being on the account as a signing key and the email being on the account. PwrGit only asks after a push the user made, about at most one of the commits they authored, at most once per launch per repository.

6 Behaviour per state, and the decisions this needs

The 2c prototype's states, written down as the contract an implementation is tested against. Recommended rule: the profile is enforced completely inside PwrGit. That means also passing -c author.* / committer.* and scrubbing GIT_AUTHOR_* / GIT_COMMITTER_* / EMAIL from PwrGit's commit spawns. Nothing then "wins" by accident, and the footer reports a resolution that cannot drift from what Git writes. Anyone who wants repo-specific identity gets it on purpose, through decision A.

6bOpen decisions, with a recommendation each
A

Enforce or explain?

Enforce completely, as above, plus an opt-in profile mode, “Follow Git in each repository”, which passes no -c at all and lets includeIf and repo config decide. The footer then names the deciding file. Explaining an inconsistent enforcement only teaches people that the footer is unreliable.

B

Is writing global config in scope?

Yes, explicitly, at a click, previewed (4b/5c). KTD4 stays true for every implicit path. Amend the plan’s KTD4 text so the next reviewer does not find a contradiction.

C

Share the profile identity with agents?

Not in this change. Setting the global identity (4b) already fixes the case that started this. Injecting GIT_AUTHOR_* into agent sessions is a cross-app contract with PwrAgent, and it needs its own design.

D

Should the rebase assistant sign?

Yes, by honouring config (finding 4). If the signer is unavailable, for example pinentry with no TTY, fail with a readable "signing failed" and offer to rebase unsigned for that run only.

E

Where should the card live?

Settings › Profiles, as drawn. The alternative is General, beside Git runtime. That groups by “machine Git facts” but splits “who do I commit as” across two pages.

6cReal-Git tests the resolver owes
✓

Isolated, always

Every fixture sets HOME, XDG_CONFIG_HOME, GIT_CONFIG_NOSYSTEM=1, and clears the identity env. Without that, the dev machine's own config leaks in.

✓

Cases

nothing set · guessed (assert useConfigOnly fails while plain passes) · XDG only · includeIf gitdir · repo · worktree with two worktrees · author.email · each env var · name missing · amend keeps author · rebase keeps authors and signs · SSH-signed header detected without allowed signers.

✓

Writes

4b's preview equals the bytes written, the target file matches Git's own --global choice, and a repo override survives a global write.
