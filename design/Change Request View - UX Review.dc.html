1Findings: a pull request row can't be selected, and the only way to look at its code is to leave the list

Every frame in this file uses orbit-deploy from Change Requests in Sidebar, turn 3. Its origin is your fork and upstream is the original, both on GitHub. The repo, its people and its diffs are invented. Specimens are light theme at shipped size, drawn from app.css. The artboard loads Google's “Geist”, so text widths can differ from the app's bundled Geist Sans by a few px.

1aFour findings
1

A PR row has no selected state

A single click on .ref-cr-row does nothing. A double-click only works when a worktree holds the head. The main pane follows one thing, selection = {repoId, worktreeId} in App.tsx. A row that is not a worktree has nothing to select, so the list behaves like a menu, not a list.

2

Looking means committing

The row's two verbs both send you away. ⌂ selects the worktree, which swaps the graph, the rail and the sidebar selection all at once. + opens New worktree, which makes a checkout on disk just to read a diff. A branch with no worktree cannot be previewed either: App.tsx says so and offers to make one.

3

The diff is usually already on this machine

For Local rows, and for any head already fetched as refs/remotes/…, both ends are in the object store. The diff is git diff base...head and needs no network at all. The open list already carries headOid, additions, deletions, changedFiles and commitCount, so the summary can show before git answers. Only unfetched heads and forks need a fetch, and that fetch does not have to make a branch.

4

Nothing remembers that you were in the list

After ⌂, the PR you came from has no selected row to return to. The section may even be scrolled away. Back Forward Navigation designs a history, but its place is a worktree selection, so a PR could not be an entry in it either.

3The PR view: one header, the diff, and the rail as its table of contents

The view is read-only and asks the forge nothing. The header comes from the cached open list, and the diff comes from git. That keeps the sidebar rule that “nothing asks a forge about one change request at a time”, so there are no per-PR API calls and no review threads. The diff is git diff <base>...<head>, measured from the merge base, which is what the forge's Files tab shows. A commit in the rail narrows it to git show <sha>.

1

Identity

The shipped PrChip at header size, plus the title, which ellipsizes and shows in full in a tooltip. With two remotes the remote chip sits on line 2 and never squeezes the title.

2

One primary verb, as words

The verb depends on where the head is: ⌂ Go to worktree, + Worktree, or Fetch when a fetch failed. ↗ opens the forge. ⋯ holds Copy branch, Copy link, Check out here (switch the current worktree), and Compare with… (deferred). At the narrowest width the verb's label drops to its glyph, the way .wt-header.fit-icons already does.

3

Facts from the list, before git answers

Author, remote, head → base, +/−, files and commits all come from the cached row, so the header paints instantly, before any fetch. Items drop from the right as width runs out: updated, then commits, then the author's name, keeping the avatar.

4Keeping your place: Back, the keyboard, and what ⌂ leaves behind

This turn composes with Back Forward Navigation, which is designed and not yet built. The one change there: a place becomes {kind: "worktree", repoId, worktreeId} or {kind: "changeRequest", repoId, forgeRepo, number}. Rows are keyed the same way, by changeRequestKey, so one branch with #412 on upstream and #14 on origin is still two places. A commit picked in the rail rides on the PR's entry rather than becoming its own, the same rule that design gives commits in the lineage.

4cOpen questions for you
A

Selecting a PR whose head a worktree holds: the PR view or the worktree?

Proposed: always the PR view, so a click means the same thing on every row, and ⌂ is one more click. The alternative saves that click and brings back the jump you didn't like.

B

Fetch on click without asking?

Proposed: yes. A click is intent, the fetch is a single ref, and it never makes a branch. Arrowing past a row waits 600 ms first (4b). Repositories in “Fetch: manual” mode would show the summary with a Fetch button instead.

C

Build order

The PR view, the selection and the rail could ship first, using today's single-entry state, with Back added when Back Forward Navigation lands. Or Back could come first, so the view is never a dead end. Proposed: the view first. ⌂ and the row stay put, so nothing is lost without Back.

D

Later, not now

Not in scope: review threads, checks detail and approve/merge, which all need per-PR forge calls. Also out: the same view for any branch (“compare with default”). The view's shape fits both, which is a reason to build it as a ref-pair view with a PR header rather than as something PR-only.

5Live: click through the list, jump to a worktree, and come back

Click any PR row to select it. #409 is unfetched and #405 and #398 are forks, so the first visit to each shows the fetch. In the PR view, ⌂ Go to worktree jumps to tenant-deploy-windows, and ‹ brings you back to the same PR. Clicking a worktree row selects it. The readout counts forge API calls made by the view; it should stay at 0.
