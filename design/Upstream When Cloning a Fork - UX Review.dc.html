1As built: cloning your fork leaves the original behind

Clone already knows when the picked repository is a fork. The source row draws the fork chip, and preflight reads parent and root from the forge. Fork… and Clone's "Your fork" card both add the original as upstream. Picking a fork directly (typing riverbend/sparkline, or finding it in search) runs a plain repo:clone, and that checkout gets origin and nothing else. Names are contrived: octo-labs/sparkline is the original, riverbend is the signed-in account, lumen-co is an org.

The "Clone from" pair doesn't apply here: that pair is for a source someone else owns, and this source is already your fork.

After the clone, main reads the remotes before adding anything. A remote that already points at the chosen original is kept under its own name (planUpstreamRemote's existing). If upstream is taken by something else, the original goes in as upstream-2. Nothing is clobbered or renamed.

3dThe clone worked and the remote didn't: keep the checkout
Cloned to ~/src/github/sparkline, but couldn't add the upstream remote

The checkout is kept and listed in the sidebar. Add octo-labs/sparkline from Refs → Remotes.

A finished transfer isn't thrown away over a remote. The repository is indexed, and the existing "Add the fork parent" offer picks it up from there.

5Build list

One request field, one main-process step, one option row. The rules go in pure helpers so they're unit-tested, not left in JSX.

#ChangeWhereTurn
Aupstream on repo:cloneOptional slug. Before transferring anything, main checks it against the source's parent/root from the forge and refuses an unrelated one, as repo:fork does. protocol.ts, clone-service.ts2a
BAdd it after the transferThe adding_upstream phase. It reads the remotes and reuses one that already points at the original (gh's). Otherwise it adds under planUpstreamRemote's name, with a URL in the protocol's form. If it fails, the checkout is kept and indexed. clone-service.ts3c, 3d
CSame reuse rule for Fork…ForkService.addUpstream ran a bare remote add upstream, which collides with gh's own on the CLI protocol. It now uses the step from B. fork-service.ts3c
DOption row in CloneChoices come from cloneUpstreamChoices (parent first, root second). On by default. Shown only for a forge source the forge calls a fork. "Will create" reads the same state. clone-from.ts, CloneRepoDialog.tsx2a, 3a, 3b
