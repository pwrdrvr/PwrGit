1 Findings — the dialog cannot find a PR that the graph behind it has already found

Typing 106 into the refs browser returns nothing, while the lineage graph under the dialog shows a #106 chip on ten of that PR’s commits. The number is already cached, but the search never looks at it. This is a join we skipped, not a missing crawl.

1aThree places the number drops out
1

Local rows match on three strings, and the PR is not one of them

RepoRefsModal filters locals in the renderer on name + upstream + subject. A local branch with an open PR that the chip in the sidebar already shows is still unfindable by its number or title.

2

Remote rows come straight from git

repo:remoteBranches pages for-each-ref output and filters it by name. Git has no PR numbers. Separately, search_fts.pr is filled only for kind = 'worktree'. The remote_branch trigger inserts NULL, so ⌘K is blind here too.

3

The branch sweep only asks about local branches

branch_pr is keyed by the branches in refs/heads. #106’s head is fetched (origin/codex/…) but has never been checked out, so the sweep has no row for it. The ask was “the branch is local”, but it is only fetched, and that is exactly the case these tables miss.

?

But commit_pr already knows

The graph resolves PRs by commit SHA. In the real repo, commit_pr holds #106 · open · head_ref codex/release-console-rebuild-plan ten times over, so the fix can start from data already on disk. It is incomplete, though: it covers only PRs whose commits someone has scrolled past.

Fork rows are why this is a tab and not a decoration. 3 The cache: one list call per repo, not a crawler

ghcrawl was hard because it wanted everything: bodies, comments, closed history, embeddings and clusters across ~12k items. This dialog needs the open set’s metadata and nothing else. That is one GraphQL page on GitHub and one REST page on GitLab, and it fits under ForgeProvider as a fifth method beside the four that exist.

3aWhat is fetched, when, and what it costs
QuestionHowWhenCost
Every open change requestfetchOpenPrs(repo). GitHub: pullRequests(states: OPEN, first: 100, orderBy: UPDATED_AT). GitLab: merge_requests?state=opened&per_page=100With the existing repo sweep (10 min TTL), on dialog open, and after a fetch1 request per repo; a second page only past 100 open
A merged or closed one, by numberfetchPrsByNumbers, which already existsOnly when a digits query misses the open list1 request per distinct miss, then cached
Branch ↔ PR linkA join on head_ref (and head_repo for forks) against local and remote branch namesAt query time, in SQLFree
A fork’s head commitsgit fetch origin pull/N/head:pr/N (or merge-requests/N/head)Only on Switch here / New worktreeOne fetch the reader asked for
Bodies, comments, reviewsNot fetched. ↗ opens the forgeNeverNone

Storage: a repo_open_pr table keyed (repo_id, number) with the PR_DETAIL_COLUMNS set plus author, head_repo, updated_at. It is replaced wholesale on each successful list, so a PR that closed simply disappears, with no tombstones. A refused or failed list writes nothing and leaves the last good set in place, per “a refusal is not an answer” in forge/AGENTS.md. The same list also fills branch_pr for any head that is a local branch, so the sidebar chips get fresher as a side effect.

3bOpen questions for Harold
A

Ship 2a first, then 2b?

2a is renderer plus one SQL join against data the list call will produce. 2b adds a tab, fork checkout and the lookup notice. They share the same cache, so the order only decides which one ships first.

B

⌘K too?

Giving search_fts a change_request kind would make 106 in the palette jump to the branch from anywhere. It is the same table, one more trigger, and the palette already has a kind-glyph slot.

C

Name the fork branch pr/121 or octo-contrib/fix/quickstart-typo?

gh pr checkout uses the head branch name, which can collide with a local one. pr/N never collides but hides what the branch is. Showing both in the row is cheap either way.

D

Draft PRs

Listed, with the shipped draft underline on the chip. Filtering them out would hide the reader’s own work in progress, which is the PR they are most likely to be looking for.
