1As built in #379: the repair is explained only in Git's own words

PR #379 repairs a checkout whose main still points at the original repository after the remotes were renamed. It shows up in three places: Pull's menu, the dialog after a refused Push, and the Remotes tab. All three describe the change as Track origin/main. That is git branch --set-upstream-to, which most people meet about once a year. Nothing on screen shows where main sends its pushes today, or where it will send them afterwards. Names are contrived: octo-labs/sparkline is the original, riverbend is the signed-in account, and riverbend/sparkline is its fork. Redrawn from the screenshots on #379.

1dWhat goes wrong
1

Every label is Git configurationUX

origin, upstream, "tracks" and "tracking" all need the reader to know that remotes are nicknames and that a branch has an upstream. People who hit this have usually just renamed a remote and don't know they did it. The button names the config, not the outcome: Track origin/main rather than "push to my fork".

2

"upstream" means two different things hereUX

The remote is named upstream (the original repository), and Git also calls a branch's tracked ref its "upstream". The Post-ship 2f copy pass started separating the two, but the dialog uses both senses in one sentence.

3

No picture of what changesGAP

Two arrows change: where main pulls from and where it pushes to. Drawn, the fix explains itself. Written as config, it reads like a risk.

4

The refusal is shouted, then unexplainedGAP

The forge's raw ERROR: line sits in an amber box with no attribution. Opened from Pull , the same box holds a sentence that isn't an error at all.

5

Only origin is ever offeredGAP

forkTrackingRepair always proposes origin/<branch>. A checkout that also has an organisation's fork you can push to gets no choice. That case is secondary: 4.

6

Three surfaces, three sets of wordsGAP

The menu, the dialog and the Remotes card each word it differently, and the Remotes card changes config without the dialog's explanation.

2Draw it: where main pulls from and pushes to, now and after

One dialog, three ways to draw the same two changes. Each draws three things: the original, this checkout, and your fork. The remote's nickname (upstream, origin) appears only as a small tag; the owner/name is the label. The button names the outcome. Git's own words move into an In Git terms disclosure, closed by default, for anyone who wants the exact command. No new IPC: ForkTrackingRepair plus repo.identity (the fork and its parent) already carry every label drawn here. After the repair, Pull still offers Sync with the original. The dotted arrow shows that it stays one click away.

4Secondary: more than one place main could push

Sometimes a checkout carries a second fork you can push to, such as an organisation's copy on a remote called lumen. Then the After strip gets a short Push to list, and the picked fork becomes the right-hand node. Your own fork on origin stays the default and the first row. With one candidate there is no list, and the dialog is 2b unchanged. This needs work in main: today remote:inspectForkTracking confirms origin only. It would have to ask the forge, for every remote whose repository is a fork of the same parent, whether you can push. One card, not one per combination.
