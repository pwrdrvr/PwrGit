1 Findings — the sidebar counts finished branches, and nothing it shows can act on them

Two reports from one screenshot. ↑2 in the Branches header says two branches have commits to push, and clicking it only folds the section. 225 gone survived a garbage collection. Garbage collection was never going to remove them: a branch name is a root of reachability, and git gc only collects what no ref reaches. fetch --prune does not remove them either. Every PwrGit fetch already passes it, and it is the step that makes a branch gone: it deletes origin/feature and leaves your feature pointing at an upstream that no longer exists. Removing these branches is the job of Maintenance › Local branches, and that review is built to decline squash merges. Repository and branch names are invented.

1cSix findings
1

The counts are not controls

They sit inside the disclosure button. A button inside a button is invalid, so the counts cannot become links where they stand. They have to move out and become siblings of the disclosure.

2

No surface lists branches by state

The six-row slice is ranked by relevance, and View all opens a refs browser that filters on text only. Nothing in the app answers “which two have something to push?”

3

“163 gone” leads nowhere

The one place that deletes gone branches is a tab behind the sidebar’s Garbage collection… button. The collection tab hides “does not remove local branch names” in a collapsed What gets cleaned up?, so running gc and expecting the count to drop is a reasonable mistake.

4

The review accepts ancestry only

scanStaleBranches requires the tip to be --merged=HEAD. A squash merge writes a new commit, so the branch’s own commits are never in main. On a repository that squash-merges, nearly every gone branch is declined, and the empty state sends you to delete them one at a time.

5

The proof is already in the database

branch_pr caches each local branch’s pull request, including merged and closed ones (state, merged_at). The review never reads it. The one missing fact is the PR’s final head commit, which would show the local tip holds nothing the PR did not.

6

No age guard and no stated “never” rules

A branch finished an hour ago is offered the same as one from last spring, and the rules that protect work (never pushed, held by a worktree) are buried in prose rather than shown as rules.

3 Evidence — what makes a gone branch safe to delete

The rule underneath all of this: a branch is offered only when every commit on it is proven to exist somewhere else. Ancestry proves it when the commits are in HEAD. For a squash merge, a merged PR whose final head commit is the local tip proves it: the PR held exactly these commits, and the forge merged them. That same proof covers “never pushed” by construction. A tip that was never pushed cannot be any PR’s head, and a branch with no upstream is never gone in the first place.

Why tip-equals-head and not “has a merged PR”. A merged PR alone proves the branch was finished once. It says nothing about the commit you made on it the next morning. The PR’s headRefOid (GitHub) or diffHeadSha (GitLab) closes that gap, and it is the one field PwrGit does not fetch today. A local tip that is an ancestor of the PR head also qualifies, because the PR contained everything local and more.

4 Maintenance › Local branches, redrawn — and garbage collection hands off to it

The dialog, tabs and bulk-sync cards stay; what changes is what the review knows. Before a review, the options become rules you can see, including the age guard as a dropdown. After a review, each repository card splits into Finished (checked, each with its evidence) and Kept (collapsed, counted by reason). A garbage-collection run now ends with an offer, because that is where people look for this.

6 What gets built

Two independent pieces. The counts-as-filters change is renderer-only and can ship first. The clean-up needs one new forge field and changes to the review.

PieceChange
Header chipsRepoRefsSections: move .ref-section__summary and .ref-section__gone out of button.ref-section__head into sibling buttons. They open the browser through the existing browserRequest path, extended from a tab to a tab plus a status filter.
Status filterRepoRefsModal: add a status filter (all | ahead | behind | gone | unpublished) applied before the text filter in localMatches, rendered as the chip row. On the Gone filter, show the banner once the renderer-side rules count at least one finished branch.
PR head commitAdd headRefOid to PR_NODE_FIELDS and diffHeadSha to the GitLab MR query. Add a migration with a head_oid column on branch_pr, and headOid? on PrSummary. Existing merged rows lack it; the review refetches those branches in one batched fetchPrsForBranches call.
Review rulesscanStaleBranches takes { prProof, touchedWithinDays } and returns every gone branch with a verdict and reason (turn 3), not only the eligible ones. StaleBranch gains evidence: "ancestry" | "pr", pr, and touchedAt. Touched comes from %(committerdate) and the newest git reflog refs/heads/<b> entry.
DeletedeleteStaleBranch rechecks the verdict. Ancestry rows use deleteLocalBranch(…, false) as today. PR rows use forceDeleteExpectedRef against the reviewed tip, which is a compare-and-swap, so a branch that moved since the review is refused as stale.
