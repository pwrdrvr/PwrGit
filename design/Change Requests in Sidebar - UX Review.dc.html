1Findings: the list already exists, behind a dialog, and it only asks origin

PwrGit already keeps every open pull request and merge request in a cache filled by one list call per repo, and it can already check out a PR's head into a worktree, including a fork's head. The sidebar does not show that list. It only shows PRs as chips on worktree rows. And because the list is only ever asked of origin, a fork never sees the PRs on the original repo.

1aWhat is there and what is in the way
+

The cache and the checkout already exist

repo_open_pr (0032), pr:openList, pr:lookup and pr:fetchHead back the refs browser's Pull requests tab. ChangeRequestTable.act() already resolves a row to a worktree, a local branch, a fetched remote branch or a fork head, and then switches to it or creates a worktree. The sidebar section draws data and calls verbs that are already built.

1

The only list view is three clicks into a modal

To get from "there's #381" to a worktree today, you expand the repo, open the refs browser, change tab, find the row, then New worktree. The sidebar can show a PR only when one of the 38 worktree rows already has it checked out.

2

The list is only asked of origin

open-pr-service.ts resolves the forge from remote get-url origin and maps heads against refs/remotes/origin. In a fork checkout (origin is yours, upstream is the original) that returns your own CI PRs and never the PR you sent upstream. A second forge remote, such as a GitLab mirror, is never asked at all.

3

The cache key cannot hold two remotes

Rows are keyed (repo_id, number). Your fork's #14 and the original's #14 would collide. The key needs the forge repository in it, so this is a migration and not just a renderer change.

+

The cost model is already right, so keep it

One list page per forge repo returns number, title, head, base, author, draft and the checks rollup in the same response. The TTL is 10 minutes. A failed list keeps the last good set. Nothing on this board adds a call per PR. See turn 5.

5API budget: list calls only, and nothing per PR

With 82 repos in a profile, a design that asked about each PR one at a time would spend GitHub's 5,000 points an hour in a single sidebar scroll. Everything this section draws comes from the list response. The only extra cost is one list call for each additional forge repository in a fork or a mirror.

Open list, per forge repoGitHub: pullRequests(states: OPEN, first: 50, orderBy: UPDATED_AT) with statusCheckRollup inline. GitLab: mergeRequests(state: opened, first: 100) with headPipelineOn repo expand with the existing sweep (10 min TTL). ⟳ asks again, with a 1 min floor. Schema: repo_open_pr gains forge_repo (host plus path) and is keyed (repo_id, forge_repo, number). repo_open_pr_state gets one TTL row per forge repo, so the fork's list and the original's list refresh and fail independently. The list for each remote replaces only that remote's rows. The resolver changes from remote get-url origin to every remote, deduplicated by forge repo, skipping hosts with no token. The same list keeps feeding branch_pr for local heads, so worktree chips also get fresher.
