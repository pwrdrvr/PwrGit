0Brief: we never built stacked PRs, and the team already stacks with gh stack

Harold, 2026-11-22: “Did we build Stacked PR GUI support and operation support in PwrGit? I feel like we didn’t.” We didn’t. PwrGit draws a stack’s branches as one lane train and prints → base on a pull-request row whose base isn’t the default branch. That’s all. Nothing stores a branch’s parent. Nothing rebases with --onto or --update-refs. Nothing opens a PR or changes its base. There’s no undo. Meanwhile PwrAgent’s contributors stack with GitHub’s own gh stack (v0.3.0). It keeps a catalog at $GIT_COMMON_DIR/gh-stack and a stack object on GitHub. Goal: make stacks something you can see and operate in PwrGit and through its MCP server, without inventing a fourth stack format. Open decisions for review: where stack state lives (1a is recommended), where stacks show (2a), and how agents get write access (5b). Everything here is a proposal. Nothing is built. All data is invented.

0aWhat PwrGit has to build on
1

PR data already carries the chain

PrSummary.baseRefName and headRefName arrive with every GraphQL fetch (pr-query.ts). Chaining base to head gives a stack’s order for free. PwrAgent’s pullRequestStackOrder() does exactly that for combined reviews.

2

The lane layout already draws a stack as a train

lane-layout.ts hands lane ownership over at a linear boundary, so stacked branches share one straight lane. We add meaning to that train. It doesn’t need new geometry.

3

Draft → check → apply already exists

History editing replays a plan in a disposable clone, proves the final tree, and returns an approvalToken before rebase:apply. Stack operations reuse that contract and its proof ledger.

4

Leased push and the operation banner

remote:pushBranchWithLease pushes with --force-with-lease=<ref>:<expected>. OperationBanner already shows an in-progress rebase with Continue and Abort.

0bWhat is missing
1

No parent, so no “needs restack”

When windows/model takes a review fix, nothing knows that windows/scheduler sits on the old tip. Its PR silently shows the parent’s old commits as its own.

2

Rebase covers the current branch only

rebaseOntoUpstream runs a plain git rebase <upstream>. Rebasing a child onto a squash-merged parent replays the parent’s commits on top of their own squash. That’s the classic stacked-PR conflict.

3

No forge writes but enqueue

PwrGit can add a PR to a merge queue, and that’s the only thing it can do on the forge. It can’t open a PR, retarget a base, or link a stack.

4

MCP is read-only, with no per-operation consent

All pwrgit_* tools read. Capabilities stop at app.navigate. An agent can see a repository but can’t restack it, and the app has no way to approve one operation.

1The model: whose stack is it?

A stack is a chain of branches. Each one’s parent is the branch below it, and the bottom one’s parent is trunk. What matters is where that chain is written down. Three tools already disagree. gh stack keeps a JSON catalog in the common Git dir and a stack object on GitHub. git-town keeps git-town-branch.<b>.parent in config. The forge only knows each PR’s base. Whatever PwrGit picks has to survive a teammate running gh stack sync in the next worktree over.

1aRecommended. Read and write gh stack’s catalog, under its locks
# $GIT_COMMON_DIR/gh-stack  (schemaVersion 1, shared by every worktree)
{
  "schemaVersion": 1,
  "repository": "github.com:acme/orbit-deploy",
  "stacks": [{
    "trunk": { "branch": "main", "head": "8c1d2e0…" },
    "branches": [
      { "branch": "windows/model",     "head": "4e1a9c2…", "base": "8c1d2e0…",
        "pullRequest": { "number": 651, "id": "PR_kw…", "url": "…/pull/651" } },
      { "branch": "windows/scheduler", "head": "9f3c2e1…", "base": "4e1a9c2…", … },
      { "branch": "windows/api",       "head": "51ad0e7…", "base": "9f3c2e1…", … },
      { "branch": "windows/ui",        "head": "0d8c6b3…", "base": "51ad0e7…" }
    ]
  }]
}
# base = the parent tip this branch was last built on: the --onto anchor
# gh-stack.lock / gh-stack-operation.lock: taken by PwrGit before any write

Why: it already exists in this team’s clones, and it already records the hard part. base is the parent tip each branch was built on, which is the exact anchor a restack needs. It lives in the common dir, so every worktree sees the same stacks. That matters most for PwrAgent, where every thread is a worktree. A gh stack view after a PwrGit restack shows the same thing PwrGit does. An unknown schemaVersion drops PwrGit to read-only. It never guesses at a newer format.

2Where stacks show: a Stacks section, a stack chip on PRs, and meaning on the lane train

The stack is the unit you restack, submit and sync, so it gets a place of its own. That’s where the verbs live. The branches inside it still appear everywhere they do today. Each picks up a position chip (2/4) that leads back to its stack. Rejected: grouping stacked PRs inside Pull requests › Local. The top of a stack usually has no PR yet, so a stack would be split across two sections.

2bThe lane train, before and after Restack

One position chip per branch chip, in the same .ref-chip budget (it takes one of the two chip slots before +N). The bracket in the right gutter marks the stack’s rows and selects the stack on click. The old tip isn’t drawn as a branch. It’s labelled for what it is, the commit the children still sit on. That’s the whole explanation of “needs restack”.

3Live: the stack view, the plan, and every operation through it

Selecting a stack opens it in the main pane, the way selecting a PR opens the PR view. Each operation stages a plan first: Restack, Sync, Submit, a drag to reorder, an MCP call from an agent. The plan is computed with git replay and git merge-tree and touches no worktree and no ref, so its conflict forecast is real. Then Run moves every ref in one transaction. Try it. Push a review fix to the bottom, Restack, Submit, then merge the bottom PR and Sync. Turn on the conflict forecast to see the paused path. Motion budget: cards re-seat in 360ms on the app’s ease-out. The running branch carries the amber scanner line. A restacked wire draws itself solid. Nothing bounces, and prefers-reduced-motion turns all of it off.

4When it goes wrong: conflicts, squash merges, other worktrees, undo

Stacked-PR tools fail at four predictable points. A replay conflicts. A squash merge leaves a child carrying commits main now has under another hash. A branch is checked out in someone else’s worktree. A push lands on a branch someone else just pushed. Each gets a rule, and the rule is what the plan shows.

4aA conflict the forecast missed: the existing operation banner, stack-aware
Restack paused at windows/api, 2 of 3. Resolve in ⌂ orbit-deploy.windows-api. windows/ui waits.

A forecast is merge-tree, so it can’t miss a textual conflict. A hook or a dirty worktree can still stop the run. Then the in-flight branch runs a real git rebase --onto in its own worktree, or in a disposable one if it isn’t checked out. Resolution goes through the shipped OperationBanner. The rest of the plan resumes from the resolved tip. The plan’s journal sits in $GIT_COMMON_DIR/pwrgit-stack-op.json, so a quit mid-conflict comes back to the same banner.

4bSync after a squash merge: exclude the parent, retarget before delete
# #651 squash-merged as 3fa9b61. windows/scheduler still contains 4e1a9c2..7b3d0f5.
git rebase origin/main windows/scheduler      # replays #651 over its own squash → conflicts
git replay --onto origin/main 7b3d0f5..windows/scheduler
                                          # 7b3d0f5 = catalog base: only #652's commits move
# forge order matters:
PATCH #652 base → main                   # 1. retarget the child first
git push origin :windows/model            # 2. only then delete; deleting an open PR's base closes it

The catalog’s base is what makes this safe without a heuristic. gh-stack v0.1.1 got the boundary wrong after a squash (upstream #586, recorded in PwrAgent’s docs/gh-stack-workflow.md). PwrGit takes the newest of the catalog base, the parent’s last-known tip, and the fork point. It then proves that the commit list it replays equals the child’s own commits by patch-id. If they differ, the plan stops before Run.

4cBranches checked out elsewhere
1

--update-refs skips them, so we don’t use it

Git won’t update a ref that’s checked out in another worktree. It warns and moves on, and the stack comes out half-restacked. PwrGit moves refs itself, in one update-ref transaction with each planned old tip as the expected value.

2

Then each checked-out worktree follows with read-tree -m -u <old> <new>

Once the ref has moved, reset --keep would see HEAD already at the target and leave the old files behind. A two-tree read-tree -m -u moves the index and files from the old tip to the new one, as a checkout does. Before Run, the plan intersects each worktree’s dirty files with the files the restack changes. An empty intersection means its changes ride along. A non-empty one blocks the whole plan before any ref moves and names the files. Stash them, or finish them, then restack.

3

An agent mid-turn is a dirty worktree with a pulse

PwrAgent will gate this harder. It won’t restack under a running turn without the thread’s consent. That’s its design to do, and it’s handed off with this board.

4dUndo, and pushing without clobbering
Restacked 3 brancheswindows/scheduler, windows/api, windows/ui
# before Run: one ref per branch, kept 14 days
refs/pwrgit/undo/op-0412/windows/scheduler → 9f3c2e1
# Undo = one transaction back, expecting the tips Run wrote
# Submit: all-or-nothing, each leased to the sha PwrGit last fetched
git push --atomic origin \
  --force-with-lease=windows/scheduler:9f3c2e1 c04b7aa:windows/scheduler …

This is PwrGit’s first real undo. Local operations undo exactly. Once a stack is pushed, Undo offers the leased push back as a separate, named step. It never pushes as a side effect. The lease always names its expected sha. A bare --force-with-lease trusts a remote-tracking ref that a background fetch may already have advanced.

5MCP: agents plan, PwrGit proves, a person (or a standing grant) applies

Every pwrgit_* tool today reads. Stacks bring the first tools that write, so the surface is small and two-phase. Plan is safe to call freely: it writes only unreachable objects. It returns the same plan the panel in turn 3 shows, with a forecast and the exact tips it expects. Apply takes the plan id and fails if any tip moved since. That one check covers stale plans, a racing human, and a racing second agent. Write capabilities are new, sensitive, and separate. Local ref moves are one grant. Pushing and forge writes are another.

6Engine, proofs, tests and phasing

The design’s claims reduce to properties a test can hold PwrGit to. The engineering detail is in docs/plans/2026-11-22-003-design-stacked-prs.md, which goes with this board.

6aThe engine, in eight lines
1

Replay in memory

git replay --onto <parent> <base>..<branch> (bundled Git 2.56). No checkout, no index, no hooks, no half-states.

2

Locate conflicts exactly

When a replay stops, git merge-tree --write-tree --name-only walks commit by commit to name the commit and files.

3

Move all or nothing

One git update-ref --stdin transaction (start / update new old / prepare / commit). The expected old values make stale plans fail.

4

Worktrees follow

read-tree -m -u <old> <new> in each checked-out worktree, after a dirty-files ∩ changed-files preflight.

5

Prove it

Each branch’s patch-id multiset is equal before and after. Commits that went empty because trunk already has them are listed, never dropped silently.

6

Push atomically, with leases

--atomic plus an explicit --force-with-lease=ref:sha per branch. Retarget PRs before deleting a merged base.

7

Share the catalog

Read and write gh stack’s schema v1 under gh-stack.lock. Refuse while gh-stack-operation.lock or a gh stack journal is active.

8

Serialize locally

Stack operations take the repository lock in WorktreeOperationQueue, then each affected worktree’s lock, in that order.

6bTests that state the rules (AGENTS.md rule 7)
M

Model test against real Git

Random sequences of commit, amend, restack, reorder, squash-merge-then-sync and undo on a temp repo, checked against a pure model of the chain. Invariants: every parent tip is an ancestor of its child. Patch-ids are preserved. Undo restores exact tips. No commit becomes unreachable from refs/pwrgit/undo.

O

gh stack as an oracle

On identical fixtures, gh stack rebase and PwrGit’s restack produce the same trees. A catalog PwrGit wrote reads back unchanged through gh stack view --json.

P

Forecast soundness

Property test: if the forecast says clean, apply doesn’t conflict. If it names files, those are the files rebase --onto stops on.

S

The squash-merge regression

The gh-stack #586 shape, rebuilt from PwrAgent’s recorded incident, must sync with zero conflicts. It must fail on a naive rebase origin/main.
