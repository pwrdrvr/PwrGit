1 Findings — a card whose loudest text is command output

PR #296 pins every PwrGit repository command to the bundled Git and Git LFS, and adds one read-only card to Settings › General to say so. Pinning the runtime is right and the card earns its place: "which Git is this actually running" was unanswerable before. What ships underneath it is four rows of raw --version stdout at 16 px, under a status chip that cannot report a status. Every specimen below is reproduced at shipped size from app.css, with the version strings the probes really return — the PR screenshot's fixture cropped the Git LFS build tail, which does not crop in the app.

Measured in the browser against the shipped stylesheets: the value is 16 px Geist 400 — larger than the 15 px section title, 28 % larger than its own 12.5 px label, and the largest text anywhere in the card. It is the only text in the body that nobody styled: control={<span>{status.bundled.git}</span>} inherits the document's 16 px, because .settings-panel__body sets no font. Four rows of stdout therefore outrank every word a person wrote.

1bFive findings
1

The value is prose where every peer is a specimen

Settings › About does this exact job one pane away, and does it in .about-identity-value — 11.5 px mono, overflow-wrap: anywhere, selectable. That class already exists in app.css. The new card reimplements half of it as an inline style object setting overflowWrap: "anywhere" on the container and skips the font entirely.

2

It prints stdout, not a version

The label already says "Bundled Git"; the value says git version 2.53.0 again. And git lfs version really returns git-lfs/3.7.1 (GitHub; darwin arm64; go 1.24.0) — platform and Go toolchain included. The PR screenshot's fixture shows a bare git-lfs/3.7.1, so the noisiest thing the card renders is the one thing the screenshot does not show.

3

The chip cannot be wrong, so it is not a status

active and default are typed "bundled" — the only value either can hold — and the renderer never reads them: the string is hardcoded. It says three things, and "Default" implies a non-default the app does not offer. Every other chip in this window reports something live: On / Off, Listening / Failed, Packaged, Stable · Latest.

4

The same sentence, four times

The description says bundled is the default. The chip says it again. Then both installed rows carry the identical two-line sub — "Discovered on the CLI search path; not used by PwrGit." — which is the tallest thing in the label column, verbatim, twice.

5

Two states have no design

See 1d. A failed probe renders a bare sentence at 16 px inside role="status" with no retry, and the probe runs once on mount — so a transient failure lasts until the window is reopened. A missing bundled Git prints "Unavailable" twice while the chip still says the runtime is in use.

2 The redraw — four changes, none of them new CSS

Every class this needs is already in app.css, and the section primitive already takes the prop. SettingsSection accepts chipKind (default / ok / warn / err); .about-identity-value is the mono value type; .settings-field__error is the red sentence; .settings-button is Retry. The work is choosing what to say, not what to build.

2aOne word that can be wrong
3Before a constant, in every state
Bundled · In use · Default
3After chipKind follows bundled.git
Bundled Unavailable Unknown

Bundled when the probe answered — the one fact the chip is for, and the one the description already explains. Unavailable, chipKind="err", when bundled.git is null: the card must look broken in the state where Git cannot run. Unknown, chipKind="warn", when the probe itself failed, which is not the same as Git being missing. "In use" and "Default" then stop competing with a description that says both in a full sentence.

If parsing is judged too clever for a diagnostic, the weaker version of this finding still holds: style the span, and the 16 px problem goes away on its own.

3 The state table, and one protocol note

Four booleans reach this card — bundled Git, bundled LFS, installed Git, installed LFS, each present or not — plus "the probe did not answer". Only two of those states are drawn today, and only one of them is right.

3aWhat the card should report, per state
StateChipBodyWhy
Probe pending
first ~50 ms after mountnoneSkeleton rowsA 16 px sentence that replaces itself is a layout jump. The row count is known before the answer is.
All four foundBundledFour rowsThe ordinary case. 2d.
Bundled found, nothing installedBundledInstalled rows read Not installedThis is fine, and must not look like a problem — it is the case the whole PR exists to make safe. Today it renders "Not found" at 16 px in primary text.
Bundled Git missingUnavailableError sentence on the Git rowNothing in PwrGit can run. 2e. Today: neutral grey, chip unchanged.
Bundled LFS missing, Git presentBundledLFS row reads Not found, plus one lineNarrower blast radius — only LFS repositories break — so it is not the card's headline, but it is not nothing either. Undrawn today.
Probe failedUnknownAlert + Retry"We could not look" is not "it is missing". 2e. Today: indistinguishable from a healthy card apart from one grey sentence.

The protocol note: git:runtimeStatus returns active: "bundled" and default: "bundled" — both typed to that single literal, and neither read by the renderer, which hardcodes the chip text instead. They are placeholders for a runtime choice the PR deliberately does not offer ("There was no existing user-facing custom Git setting"). Either the chip should derive from them, or they should come out until something can vary; two fields that can only hold one value will not survive contact with the first person who tries to add a second runtime, because nothing today proves the UI would notice.
