1Where a picture of the route helps, and where it doesn't

The route from Fork Tracking Repair 2b draws three things: the original, this checkout, and your fork, with the branch's Push and Pull as arrows between them. This turn checks each place in PwrGit that decides or explains where a branch pulls from and pushes to, against the code on main after #378 and #379. The picture goes only where a reader has to know which repository a nickname stands for in order to act. Two forms: the full route where there is room and a decision, and a one-line route where the space is a menu row. Names are contrived: octo-labs/sparkline is the original (remote upstream), riverbend/sparkline is the fork (remote origin), and riverbend is signed in. "Can't push" and "you can push" appear only where PwrGit has asked: viewerCanPush is known for origin alone.

1cWhat the survey found
1

Nothing says where a branch pushesGAP

Pull's menu details and the header chip's tooltip imply it. Push's own tooltip is just "Push". The only plain answer is the branch table's Upstream column, which reads origin/main.

2

Fork… describes remotes, not the branchUX

"origin riverbend/sparkline" is accurate, but the reader has to know that main follows origin. Forking in place never touches tracking. The nickname moves underneath the branch, and that is the hard part to picture.

3

Publish doesn't know it's on a forkGAP

The rows are nicknames and push URLs, and the default is whichever remote is called origin. When repo.identity already says viewerCanPush: false, Publish still offers the push and lets it be refused.

4

Remotes tab roles come from namesUX

A card says Upstream because the remote is called upstream. repo.identity.parent already says which remote is the original: forkTrackingRepair matches it with parseForgeRemote.

5

Two places to leave alone

Clone's cards already are the picture. Reset isn't a route question at all.

3Publish: name the repositories, and draw where the branch will go

The rows keep the radio and the default (origin), but lead with owner/name and say what each repository is: Your fork, The original or just a name. Below them, one After strip follows the pick. The strip appears only when it explains something: on a fork, or when GitHub has said you can't push to origin. A plain repository with one remote you can push to keeps today's dialog. Data: the dialog gains repo.identity from the header and labels each remote with parseForgeRemote against identity and identity.parent. That runs in the renderer, so no new IPC. Only origin gets a push pill.

4Remotes tab: the fork card always shows the route

Today the card says a fork was recognised and stops there. Proposed: whenever identity.parent is known, the card draws the focused branch's route as it is now, in plain grey, with no Now or After. The remote cards below take their role from the same match instead of from the name, so a remote called upstream that isn't the parent no longer reads "Upstream". When the route needs repair, the card shows the wrong route, and its button opens the Fork Tracking Repair dialog (that review's 5b). Data: repo.identity, refs.branches[].upstream for the focused branch, and refs.remotes URLs. All of it is already in RepoRefsModal.
