1Why the section headings collide, clip and wrap

The operator, on the repository index build: “looks mashed up?” then “it just keeps getting worse… We might need to rekey our breakpoints to be on the size of the sidebar that is allocated to that section… the centering and line breaking is just weird. Should maybe drop to icons at narrow widths and start hiding some details we can’t fit?” Every specimen below is the app’s own heading CSS, copied from app.css and rendered at the widths a sidebar actually gives a section row. A section row is the tree’s width less 50 px: 270 at the 320 px default with the index off (main today), 222 at a 400 px sidebar with the index (the screenshot), 194 at the 320 px default with the index on, 190 at the 240 px floor. Repositories and counts are invented.

1eWhat is wrong, measured
1

The Branches total is allowed to shrink, and nothing clips it

.ref-section__head is width: 100%; min-width: 0 with the default flex-shrink: 1, and the chips beside it are rigid. Below 306 px the button takes the whole shortfall and its text paints under the chips: 32 px of overlap at 270, 80 at 222, 94 at 194. Measured in a Vite build of app.css with the bundled Geist.

2

The “on main” variant hides counts to avoid the overlap

It made the total rigid and gave the chips overflow: hidden, commented as a last resort at the narrowest sidebar. At 222 it already shows 21 of “43 gone”’s 54 px, which reads as “43”; at 194 the chip is gone entirely, with no sign that anything is missing.

3

Labels can wrap, and a button centres its text

No heading label has white-space: nowrap, and the user agent centres a button’s text, so “Pull requests” breaks into two centred lines from 222 px down inside a 31 px row. That is the “centering and line breaking”.

4

The repository row spends its width on decoration first

Only the name may shrink, so at the default width with the index on, “atlas-api-gateway” ellipsizes while two forge marks, “279 wts” and the star all stay whole.

5

None of these rows has a breakpoint at all

No rule fires for them; this is what flexbox does when it runs out of room. The tree is described as built for 240 px (SIDEBAR_MIN_WIDTH), but at 240 its section rows are 190 px and all three fail. The bugs are older than the index (main at 320 already overlaps by 32 px for a repository with three counts), but the index turned the narrow case into the default: at 320 it leaves the tree 244 px.

2Four ways to fit a heading into its section

All four start from the same hygiene: the total never shrinks, no label wraps, text starts at the left, and nothing paints over anything. They differ in what decides when a heading gives something up, and what it gives up. Each is drawn at 222 and 194 px with the busiest repository, plus a quiet one where it matters.

32c in detail: the ladder, its order, and where every hidden count still lives

Information outlasts decoration: words go before counts, and a count that leaves the heading is still one hover and one click away. The steps apply to a whole repository block at once, so its five headings never mix words and glyphs. The block is measured on the section width the tree actually gives it; .sidebar__tree-pane already sizes the tree on its own, without the index.

✓

Everything a step acts on is rigid

flex: 0 0 auto, the hook’s own contract: a shrinkable item never overflows, so the block would read as fitting while it ellipsized. The total, every chip, ⟳ and Recent are rigid; only “on main” is leftover.

✓

Nothing wraps, nothing centres, nothing overlaps

white-space: nowrap and text-align: start on every label and count. The row is overflow: hidden, so even past the last step it clips at its own edge.

✓

Measured, never a constant

A ResizeObserver on the block, plus a re-fit after every render, as useStepLadder already does. The steps follow the text size axis and every count without a single number in CSS.

✓

A hidden count is never silent

A +N chip replaces whatever folded, says what it holds on hover, and opens the refs browser where every count is a filter.

Widths in px, measured in a Vite build of the real app.css with the bundled Geist Sans and Geist Mono. This artboard loads Google Fonts’ Geist, which can differ by a few pixels. Its ladder specimens are not drawn at a fixed step: each one runs the ladder when the page loads and stops where it fits in this font, which is the point of measuring.

5Build list, and three questions for the operator

The CSS hygiene alone removes every overlap and wrap and can ship first; the ladder then stops anything falling off the edge.

5aBuild, in order
1

Heading hygiene (CSS only)

.ref-section__head stops shrinking (flex: 1 0 auto, width: auto); labels and counts take nowrap and text-align: start; the chips lose the “last resort” clip; the row clips at its own edge. Fixes 1a and 1c outright.

2

One ladder per repository block

Wrap the sections RepoRow draws (Worktrees, RepoChangeRequestSection, RepoRefsSections) in one .repo-sections element and run useStepLadder on it, with a fit test of “every .ref-section__head-wrap has its content inside its box”. The steps are the classes in 3a.

3

Glyph labels and short nouns

Each heading draws its glyph and its short noun hidden beside the words; the step classes swap which one shows. Move the palette’s pull request mark into lib/; draw a remote mark and check it as a 15 px raster beside its neighbours (styles/AGENTS.md). Accessible names keep the full words.

4

The +N chip

A ref-section__chip that opens the refs browser on Branches; its hover card and aria-label list the folded counts.

5

The repository row’s two steps

useStepLadder on the row with “the name is whole” as the fit test (the Worktree row’s branch name already works this way), steps rr-no-marks, rr-short-count.

6

A harness test at 270, 222, 194 and 170

Asserts no overlap, no wrapped label and no clipped chip, by laying each text out off-screen in its computed font and comparing with its box, not by scrollWidth, which rounds a sub-pixel ellipsis away.

5bOpen questions
?

Steps per repository, or across the whole tree?

Recommended per repository, as drawn: a quiet repository keeps its words. Across the tree, every block would switch to glyphs together whenever any one needed it, which is steadier but costs the quiet ones their words.

?

Does the index keep the tree’s 240 px floor?

With this ladder a 190 px section row holds everything, so the floor becomes true. Recommended: keep 240.

?

What does +N open?

Recommended: the refs browser on Branches, unfiltered, since +N can hold more than one status. The alternative is a small menu of the folded chips, each opening its own filter.
