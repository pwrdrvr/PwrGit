1Findings: two reports, one assumption

Both reports come from disktree, which has three remotes and three mains: Harold’s old fork, the source it was forked from, and pwrdrvr/PwrDisk, the maintained fork that is now the project’s home. PwrGit assumes a repository has one remote that matters for a branch name, and a fork’s main mirrors its source. Neither holds here. Turns 1–3 use the remote names from the first report (before the rename), and turn 4 uses the names after it.

1

Same name means duplicate

BranchSwitcher drops a remote branch when localNames.has(name without its remote). That is only true for the remote the local branch tracks. Every other remote’s main disappears with it. Branch Switching turn 2c wrote this rule for origin, and it never considered a second remote.

2

Showing the row would not be enough

Picking a remote row runs git switch with the remote prefix stripped, so pwrdisk/main becomes git switch main. That lands on the existing main, still tracking origin. Nothing in the app can move a branch to a different remote.

3

Where the tracking already shows, it is plain text

“· tracks origin/main” is the one place the switcher says where main comes from, and it is the natural place to change it. The fix in turn 2 turns that text into a control.

2The row: “tracks origin/main” becomes a split chip

A remote branch with the same name as a local branch stops being a hidden row and becomes an option in that branch’s chip. The list stays as quiet as it is today (one row per name), and every remote’s copy can be reached from it. A remote branch with no local counterpart stays a row with the remote badge, unchanged. The chip is the split control from Sync Split Button, at pill radius and the row’s mono size. The left zone shows what the branch tracks, and the caret zone opens the choice.

1

The rule, restated

A remote branch is hidden only if a local branch tracks exactly that ref. Otherwise, a same-named remote copy becomes one of the local branch’s chip options, and a remote branch with no local namesake stays its own row. origin/main is still hidden, and pwrdisk/main and upstream/main are now reachable. The sidebar’s Remotes preview only ranks by this rule and hides nothing, so it is unaffected.

2

A changed chip is visibly changed

Chosen but not yet confirmed, the chip goes accent, its verb changes from “tracks” to “track”, and the count beside it says what would arrive. The footer’s Enter now says review tracking change. Enter never moves anything. It always opens turn 3’s review.

3

Keyboard

The search field keeps focus as it does today. → opens the selected row’s chip, ↑↓ pick a remote, ↵ reviews it, and ← or esc closes the menu. The shortcut lives in the chip’s tooltip (“Track another remote (→)”) and the footer, never on the chip.

4

The menu’s relation column

The relation column uses the Reset to Remote vocabulary: same commit, ↓N fast-forward, ↑N you’re ahead, ↑N ↓M diverged. These are local reads (rev-list --left-right --count per same-named ref), computed when the menu opens. “you can’t push” comes from the forge identity that already draws the read-only mark.

5

Width

The panel is min(620px, 92vw). The branch name shrinks first, as today. Then the chip text steps down from tracks origin/fix/… to the remote’s name alone, measured, never by a fixed breakpoint. The caret zone never goes.

3The review: one step inside the switcher, four shapes

Changing what a branch tracks also changes where Pull and Push go, so it always asks. The question replaces the list in the same overlay, and esc goes back to the list rather than out. Its content depends only on how the local branch and the chosen ref relate. Each version says three things: which commits move, where Pull and Push go afterwards, and what happens to uncommitted changes. Nothing is stashed up front. The tip moves with merge --ff-only or reset --keep, which keep uncommitted changes and refuse, touching nothing, when a changed file would be overwritten. Only that refusal opens the existing Bring / Leave prompt (Branch Switching turn 5, src/main/git/AGENTS.md).

1

The defaults never lose anything

A fast-forward moves by default because nothing can leave. If main is ahead or diverged, the default is track only, and moving the tip is the second choice. 3d has no choice that drops a commit outright. The worst it does is file the commit on a named branch.

2

Where the leaving commits still are

“Both are on origin/main” is rev-list main --not pwrdisk/main checked against every remote-tracking ref. Saying where they live is what makes the second choice in 3c safe to offer.

3

It is re-read before it runs

As in Reset to Remote, both tips are re-read under the repository lock. If either moved since the review was drawn, it stops with “main or pwrdisk/main changed. Nothing was changed.” It runs one operation, not three dispatches from the renderer.

4

A branch held by another worktree

If you pick a different branch’s chip and that branch is checked out elsewhere, the tracking change is still allowed. It is config only. A tip move is not, because Git refuses branch -f there. The Move choice then reads “Open the worktree that has it”, the same navigation checked_out_elsewhere already does.

5

Reused, not rebuilt

The route boxes come from Fork Tracking Repair, the ledger from Reset to Remote, and the dirty refusal from guardedSwitchBranch. In main, the tracking change is repairForkTracking generalised to any remote.

4Pull on a fork that has moved on from its source

After the rename, origin is pwrdrvr/PwrDisk, huntharo is the old fork, and upstream is still tobi/disktree. The forge says PwrDisk is a fork of tobi/disktree, so Pull treats main as a mirror. Pull’s choice on a fork defaults to sync (PULL_CHOICE_DEFAULT): fast-forward from the source, then push the same commits on to the tracked branch. The first Pull after the rename was saved by the fallback (tobi had nothing new and main was behind origin/main, so it pulled origin). The second found main level with origin/main, ran sync, and reported a problem that did not exist.

1

Nothing was wrong

main, origin/main and the worktree were all at 40b87fb. A no-op was painted in danger red, flashed “pulled · not pushed” in warning, and the card stays up until dismissed (forkSyncReceipt’s stands).

2

It measured the wrong pair

The push-back compares origin/main with the source, not with main. Pushing tobi’s tip to PwrDisk would force over 7 merged PRs, so it correctly refused, then reported the refusal as if it were the user’s problem.

3

The premise is false for this fork

A mirror fork’s main is its source’s main, maybe a little behind. PwrDisk’s is tobi’s main plus 7 merged pull requests of its own. It has become its own project, and the sync model cannot do anything useful for it.

4

It gets dangerous the day tobi pushes

Then main has commits the source lacks and the source has commits main lacks (hasOwnCommits), so Pull “stops for a rebase review”. Both offered ends, rebase and reset, rewrite pwrdrvr/PwrDisk’s published main. Harold’s ask: don’t pull, rebase or reset main and push it here.

5

“was not pushed” names no next step

There is no button, no explanation of why, and no way to stop it happening on the next Pull.

3

Harold’s plan for a maintained fork: agents evaluate each tobi/disktree pull request and port the ones worth having as PwrDisk PRs. There is no merge or rebase of upstream into main. So the Pull menu offers no upstream operation for a moved-on fork. PwrGit’s only job is to say that upstream moved: the header’s upstream +N chip and the menu’s Watching line.
