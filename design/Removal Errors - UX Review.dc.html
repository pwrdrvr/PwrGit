1 As built: a 34 s beachball, a raw error in a stacked dialog, then one red sentence that names nothing

Repository maintenance › Combined › step 1. One finished worktree is selected and removed. Its folder holds a Go module cache, and Go makes those directories read-only. git worktree remove deletes part of the tree, fails on Permission denied, and has already unregistered the worktree by then. PwrGit falls back to a synchronous rmSync with retries on the main process, so the whole app stops responding, and the delete still fails. 20 MB stays on disk. Nothing is written to Help › Logs. Redrawn in the dark theme the report came from, with invented names: acme-tap, fix/cache-installer, /Users/dev/.worktrees/k3x9/acme-tap.

1cFindings
1

The real message comes first, then disappears

The only words that say what happened appear in a modal you can only dismiss. After OK they are gone. They were never logged, so Help › Logs has nothing either.

2

The sentence that stays names nothing

“Some worktrees were not removed” doesn’t say which one, why, where its folder is, how much is left, or what to do. “Continue without further pruning” points at a button that isn’t labelled that way (the footer says Skip worktrees).

2

It is styled as a stack trace and sits on the dialog’s edge

.modal__error is 11 px Geist Mono in --danger-text with no box. Its inset rule, .prune > .modal__error, never matches: the panel is .prune__panel inside .maintenance. So it gets 10 px on top, nothing on either side, and starts at x = 0. Every other block in the panel is inset 18 px.

3

The list says nothing happened

No worktree:removed event fired, so the row stays at its old 102 MB, checkbox and all. After Re-read all it vanishes, because Git no longer lists it. That leaves 20 MB on disk that nothing in the app points to.

4

The app froze, and nothing said it was working

While rmSync ran on the main process, the button only said Removing…. There was no worktree name, no count, no time, and no way to tell a slow delete from a hang.

5

A known cause, reported as a mystery

A Go module cache is read-only on purpose. A delete that knows this can make it writable first, and one that doesn’t can at least say so: “the folder is read-only or in use”.

2 Removing: progress lives in the dialog, and the app keeps working

The delete becomes PwrGit’s own: unlink and rmdir per entry, four at a time, off the UI path. It makes read-only folders writable before deleting them. It reports progress per worktree, so the status card that said Sweep finished becomes the run’s live card, the same shape as Bulk Sync Progress 2b. It shows which worktree, files deleted so far, and N of M. Rows stay in place and say what happened to each, instead of silently leaving.

3 Partial failure: say which, why, what’s left, and what to do, inline

Two of three worktrees are removed and one is not. No dialog appears. The status card becomes the receipt, and an outcome card takes the slot where the red sentence was, inset like everything else. It names each worktree that wasn’t removed, gives a plain-language reason, the path, and what’s left on disk, then offers Reveal in Finder and Retry. Git’s or Node’s own words go in Details, and every failure is in Help › Logs. Three placements follow, with 3a recommended.

5cCopy rules, and the reason for each failure
1

Headline = count + object + what happened

“1 worktree wasn’t removed”, “2 branches weren’t deleted”, “Garbage collection failed in 1 repository”. Sentence case, no “Error:”, no exclamation mark, no “Some”.

2

Sub = what’s left + whether you can go on

“Its folder is still on disk. The other 2 were removed, and you can continue.” Name the next action only if it’s in the footer, and with the footer’s own label.

3

Reason = a plain lead phrase, then the cause

Lead with what failed (“Permission denied”, “A file is in use”), then an em dash and the likely cause in everyday words. Add one instruction only when the fix is the user’s: “close it, then retry”.

4

Raw text never leads

Error codes, syscalls, stderr and stack frames go in Details and the log, nowhere else. An unmapped error gets “Couldn’t delete the folder” plus Details, not the raw message as the reason.

5

Name things the way the list does

repo · branch exactly as the Finished row printed it, the same path, and sizes from formatBytes. The user should be able to match a failure to the row they ticked.
