2 Proposed — hosts, discovered from the repos you already have

The unit is the host, not the forge. Rows are derived from the origin of every indexed repository, so the list needs no typing and cannot drift from reality: a host appears because your code is there. Each row states its own evidence — how many repositories put it on this list, which account answered, and where that credential came from. Both CLIs are already multi-host (gh auth token --hostname, glab config get token --host), so every row is one CLI call, not a login PwrGit owns.

Why the list is derived rather than typed. A hand-maintained host list is a second source of truth that starts wrong and rots: it can name a host you no longer use, and it is silent about the one you cloned this morning. Deriving it from origin means the pane cannot omit a host that matters, and the evidence line (“6 repositories”) is the answer to the only question a surprising row raises. Add a host… exists for the one case derivation cannot cover — signing in before the first clone.

Off has to be enforced below the UI. The switch gates four places, not one: resolveForge (status), resolveForgeRepo in commit-author identity (avatars), ForgeRepoRegistry (clone and fork), and the status probe itself. An “off” that still spawns a CLI is a setting that lies. ForgeRepoRegistry is keyed by forge kind today and has to be rekeyed by hostname for any of this to work — that is the one structural change under this screen.
3 Later — signing in without a CLI

Not this change. Shown because the row above has to leave room for it: some operators will want PwrGit signed in without configuring gh or glab at all, the way VS Code does. The row already carries a credential source — today it always reads gh or glab. Adding a second source fills that slot instead of re-opening the layout.

Two sources, one row, and a visible winner. When a host has both a CLI login and a PwrGit sign-in, the row must name which one answered — otherwise revoking the wrong one looks like a bug. The open question this screen does not settle: a PwrGit-owned token has to live somewhere, which means OS keychain storage and refresh become ours, and the credential-opaque property the identity transports rely on today (gh api / glab api, no token extracted) would need a deliberate answer rather than an accident.
