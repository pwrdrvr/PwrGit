3 Review of the build: the sync works, and almost nobody can see it

On a real fork the build detected the source, fetched it, and counted main 25 commits behind upstream/main. It lit Pull and grew the arrow, and Pull's default would have synced. None of that reached the user. The chip that says so is hidden at the stock window width, Pull has no tooltip, the collapsed panel's button covers the toolbar, and the sidebar still counts against the fork alone. 2h specified the 680px cut, so part of this is the artboard's fault; this turn supersedes it. How 3 became 7, then 0. The count was stored when someone last looked. Agents then fetched, which moved origin/main, and later one of them pulled in the main checkout. Expanding the row re-read it (7). Fetching with main selected re-read it again, and by then it was 0: either an agent had already pulled, or a pruned upstream read as 0. Nothing was wrong with the fetch; the number was just old. What detects outside changes cheaply. The app avoids filesystem watchers on purpose, because recursive watches pegged fseventd on large trees. So follow the pattern StashWatch already uses: fingerprint each visible repo's refs with one for-each-ref over refs/heads and refs/remotes, or stat the mtimes of packed-refs, FETCH_HEAD and HEAD without spawning anything. Only a repo whose fingerprint moved pays for git status on its worktrees. Rows are marked visible with one shared IntersectionObserver, and the renderer only reports which rows are visible. Main owns the schedule and caps how many Git processes run, as the git layer's rule requires.

1 Where “catch up with upstream” lives

On a fork, main tracks origin/main, which is the user's own copy. Every sync signal in the header measured against it, so the header read up to date while upstream/main was 10 commits ahead. Fetch never asked upstream either, so nothing in the app could notice. The only sign was a run of dashed lanes in the graph, and nothing there acted on them.

The three tips, in the reported case

main

Checked out. Tracks origin/main.

origin/main

The user's fork. Identical to main, so the header said up to date.

upstream/main

The source. 10 commits ahead of both, and the only tip that mattered.

When main holds nothing the source lacks, catching up takes two fast-forwards: main to upstream/main, then origin/main to the same tip. Nothing leaves either branch, so no review is needed. That's what makes a one-click answer safe.
