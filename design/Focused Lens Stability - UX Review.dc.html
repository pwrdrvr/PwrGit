1 Findings — the lens re‑sorts in response to being read

The Focused lens ranks repositories on a five‑rule ladder, and the first rule is the current selection. So the act of clicking a row changes that row's rank — it is promoted to the top and every row it passes shifts down. The list is correct; the interaction is not. Specimens below are drawn at shipped size from styles/tokens.css and app.css, on contrived repository names.

Two of the five rules are written by the pointer. Selecting a worktree sets current on its repo, and the same selection is durably recorded as a visit, which sets viewed on the repo it just left. One click can therefore move two rows.

The red rules mark every row whose position changed. The target of the click travelled four rows up and out from under the cursor, and an unrelated repository slid into the slot the pointer is still sitting in — so a double‑click, or a quick second click to expand what you just opened, acts on delta‑svc.

1cWhat is actually wrong
1

The list answers a question by re‑asking it

“What am I working on” is a good question for a lens to answer. Re‑answering it on the click that acts on the answer makes the list unreadable: every interaction invalidates the map you used to aim.

2

The cost is a wrong‑target click, not just a jolt

Rows are 26 px tall and flush against each other. A promotion of four ranks puts a different repository under a stationary pointer, and nothing about the row says it is new there.

3

It repeats one level down

Inside an expanded repo, selecting a worktree promotes it out of More worktrees into the Working block. Same rule, same ladder, same jump — and it crosses a heading, so the row changes what section it claims to belong to.

4

Not only clicks

A background refresh that lands a new lastActivityAt re‑sorts the same list with no interaction at all. Any fix scoped to the click leaves that half standing.

2 When may the list re‑sort?

The ladder is not the problem and must not change — it is the lens. The only question is when a newer order is allowed to become visible. Three answers, and the one PwrAgnt's navigation sidebar already settled on.

2aSort once, then never again
Option freeze at mount; re‑sort on lens switch only

Nothing ever moves. It is also the end of the lens: a repository you start working in stays wherever it was an hour ago, and the “current” rule — the whole reason Focused is not just a recency list — never fires while you can see it.

×Rejected — cures the symptom by removing the feature
2bAnimate the move
Option FLIP the rows to their new slots

Makes the move legible and keeps the ladder honest. It does not make it safe: at the end of the animation the wrong repository is still under the pointer, and the click that lands mid‑flight is worse than one that lands after. Motion answers “what happened”; it cannot answer “what am I about to click”.

×Rejected — prettier, not safer
2cHold under the pointer; newcomers to the bottom
Chosen order computed always, shown when the pointer is away

The pointer is the one honest signal for “a human is reading this right now”. While it rests on the tree, the order it arrived on is held. Rows the lens has since added land at the bottom — the one place where arriving cannot move what is being read. Rows that genuinely left are dropped, so the lens stays the authority on membership and only position is held. Moving off the list reveals the newest order in one render.

It covers finding 4 for free: a background refresh is held by the same rule, because the hold is on the rendered order rather than on the click.

3 The hold's edges

A hold that never lets go is its own defect. The line is authorship: a change the user watched waits for the pointer to leave; a change the user made is shown at once, because holding it would look like the app ignoring them.

3aWhat cuts through the hold, and what does not
Event while the pointer rests on the listHoldWhy
Click a row — selection movesHoldsThe reason the hold exists. The row keeps its slot; the selected tint still lands on it.
Background refresh, new activityHoldsNothing the user did. Same rule, no special case.
A repository enters the lensAppendsLands at the bottom, where arriving moves nothing.
A repository leaves the lensDropsPosition is held; membership is not. A ghost row would be a lie.
Pin or unpin from the row's starHoldsIn Pinned the row simply leaves; the rest of the list does not re‑sort around it.
Switch lensReleasesA new question deserves its own answer, not a merge into the old one.
Drag‑reorder, or ⌘⇧↑/↓ReleasesThe ids are unchanged and only moved, so a held order would silently undo the drop.
Touch, anywhereNever holdsA touch has no hover to rest in — it would enter and never leave.
3bThe hold is silent, on purpose
✓

No badge, no shade, no “paused” chip

The held state is the state the user is already looking at. Marking it would announce a mechanism the user never asked about, on the surface they are trying to read — and it would appear and vanish with every pass of the mouse.

?

Nothing announces the catch‑up either

The list settles when the pointer leaves, which is the moment the user has stopped reading it. A live region here would speak over that: order is not content, and screen‑reader navigation never holds, because it never hovers.

?

One open edge

A ⌘K pick made while the pointer is parked on the list can target a repository ranked below the Focused fold. Held, it stays hidden until the pointer moves, then rises and scrolls into view. Self‑healing, and narrow enough to leave alone rather than special‑case.
