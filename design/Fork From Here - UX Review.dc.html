1What happened on sparkline: a missed lookup and a missing verb

The report: a checkout of someone else's repository, added from Add folders… two days after the PwrGit window opened. Forge identity is read when the window mounts, after a fetch, and after a clone or fork. None of those had happened, so PwrGit never learned what origin is. Every fork affordance waits on that answer, so none of them appeared. In the reporting profile, every repository without an identity row had been added after the window mounted. Names here are contrived: sparkline stands in for the reported checkout.

1bWhy each place came up empty
1

No identity for a repo added mid-sessionBUG

useRepoTree asks repo:refreshIdentities once, on mount. A repo:changed reload that brings in new rows never asks about them. Relaunching or fetching the repo would have fixed it, and nothing on screen says so.

2

Top Fork… seeds only from identityBUG

forkSeedFromRepo returns null without an identity, so the dialog opens on an empty search. The slug was already known locally: origin's URL parses to github.com/octo-labs/sparkline, and the dialog's own preflight fills in the rest.

3

The origin row's fork button waits for "can't push"GAP

The button only draws when viewerCanPush === false. "Not looked up" and "you can push" both hide it. So the one remote row that is about forking offers only Fetch.

4

A repo has no menu of its ownGAP

Worktree rows have a kebab and a right-click menu; repo rows have neither. When the read-only mark isn't drawn, there is no row-level verb left to hold Fork. design/fork-flow never drew one either: its only entry was the Clone/Fork pair at the top of the sidebar.

2Put Fork wherever you'd look for it, and don't gate it on the forge

Three places, all built from existing house parts: the .kebab and .pop-menu that worktree rows already use, the .ref-mini-action beside Fetch, and the toolbar kebab in the worktree header. Each opens the in-place fork dialog, ForkCheckoutDialog. It reads origin itself, so it works before the forge has answered. When you can push, it words itself "Fork X and point this checkout at your own copy".

3Fork… at the top starts from the repo you're on

The global button stays a Fork & clone launcher next to Clone…. With a repo selected, it now opens on that repo every time: seeded from identity when there is one, and otherwise from origin's URL, which the preflight upgrades the same way it upgrades a pasted slug. The new row between the source and the options points to the other half of the operation. You already have this checked out, so you may want to fork in place rather than clone a second copy.

3bWhat the top button opens on
✓

Repo selected, identity known

Seeded from identity, as shipped. Visibility, lineage and push access read correctly from the first frame.

✓

Repo selected, identity missing

New. One git remote -v, and origin's fetch URL parsed with the forge host map. Visibility reads "checking…" until the preflight lands. This also queues an identity refresh for the repo, so the sidebar marks catch up.

✓

origin isn't on a forge, or there's no origin

Empty search, as today. A NAS remote is not a forge, and inventing a host is how a fork lands on the wrong instance.

✓

Nothing selected

Empty search, as today.
